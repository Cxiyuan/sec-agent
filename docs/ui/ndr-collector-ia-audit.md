## 0. 结论摘要（先看这 6 条）

1. **最危险的不是措辞，是"恒 0 的仪表"**。派工模式**是默认配置**（`analysis.enabled` 默认 `true`，`app/analysis/params.py:31`）。`app/detector/runner.py:324-332`：`if analysis_params.enabled(): continue` 之后才是 `digest_q.push(...)`、`stats["digest"] += 1`、`mark_digest(stats, digest)`（`:332`）—— 而 `mark_digest`（`app/detector/history.py:41-51`）**是全仓唯一**写 `digest_sev_*` 与 `rule_*` 两个计数器族的地方（Grep 已复核，写入点唯一）。于是总览页「24h 摘要」「待聚合队列」「本分钟投递」「投递额度圆环」「24h 严重度分布」「规则 TOP 15」**六个读数**在默认部署下**结构性恒为 0 / 恒为空**（`components/status-panel.tsx:368,252-257,529-534,447-460`）。而命中线还是活的（`runner.py:988`），于是页面看起来像"有流量、但没规则命中、没严重事件" —— 比全空更像真的。
2. **事件中心的「级别」列（现名「严重度」）是混合来源，其中一半是 NDR 自己写的判断**。`feature_match` 行确为签名自带级别；`baseline_deviation`（画像异常）行是 `hits.py:609` `rule_severity=_severity_of_risk(risk)` 按风险分换算（阈值 `:572-577`），数值 2σ 行是 `:643` 硬编码 `"high"`。这正是 D2 明令禁止的"NDR 写威胁语义" —— **前端改不了，必须后端整改**（P0-3 第 5 条）。界面端能做的是：列名降为「级别」、空心徽章、tooltip 双来源（`components/events-panel.tsx:166`、`:291`、`:603-606`）。
3. **归属（谁判的、怎么结束的、花了多少、影响哪些资产）在事件侧完全缺失**。`/api/detector/hits/{id}` 只回事件本身（`app/api/routes/detector.py:495-498` → `hits.get_hit`，不 join `analysis_results`）；事件详情抽屉里只有"处理记录"（仅已忽略时才有，`components/events-panel.tsx:240-242`）。契约第 4 节要求 `terminal_reason` 让用户分清"查了没证据"和"根本没查完" —— 事件侧现在是这两个都看不到。
4. **派工队列本身口径对，但把契约里最关键的 `terminal_reason` 漏在接口外**。后端 `_result_dict` 明明返回了它（`app/analysis/queue.py:1018`），但 `/api/analysis/results` 自己另写了一份 dict，**没带**（`app/api/routes/analysis.py:134-152`）。所以派工队列"任务结论"表只有 verdict/confidence/证据条数/耗时/结论人（`components/analysis-panel.tsx:1009-1046`），恰好缺了判断"该不该追加预算"的那个字段。
5. **`/config/agent`（智能体对接）整页仍是摘要推送语义**，包括"单次最多推多少条摘要"（`components/agent-push-panel.tsx:318-325`）这种对新载荷已无意义的参数、以及"检测器命中后把聚合摘要 POST 给智能体"（`:186-193`）。顶栏告警也还在喊"摘要推送未启用：命中的摘要不会进入分析"（`components/topbar.tsx:73-80`）—— 派工模式下这是**纯粹假警报**（不需要摘要）。
6. **IA 上只需要动一处**：`事件中心`从一级菜单降为「分析中心 → 命中事件」。其余 20 页里 14 页与"谁下判断"无关，应当明确判「保留」，不要顺手重排（但"保留"必须经 Grep 工具复核 —— v1.1 就有两页因为 shell `grep` 空输出被错判为保留，见附录 A.2）。

## 1. 基准：新架构下 NDR 不做什么

这三条是判定所有页面的尺子。凡界面表达与之冲突，一律按"改"处理。

### 红线一｜NDR 不产出威胁语义

NDR 的出口只有两样东西：**客观线索**（`kind + strength + hint`，hint 里只有均值/当前值/p 值/是否首见）和**一声门铃**（恰好 5 个字段，不含任何事件内容）。它不写 `verdict`、不写"这是攻击"、不写"建议处置"。

推论到界面：
- 任何把"规则命中"直接叫作「威胁」「安全事件」「高危」的地方，都在替智能体下判断；
- `rule_severity` 是**混合来源**字段（签名自带 / 按画像风险换算 / 2σ 硬编码 `high`，见 P0-3），其中两种由 NDR 自己写入 —— 既已违反 D2，就不能再当"既定事实"展示，列名要退到「级别」、配色要去掉实心底、并显式标注"非本次判定"；
- 门铃载荷里没有事件内容，所以界面**不能**暗示"推送了什么事件"。

### 红线二｜NDR 不替智能体决定看什么

队列里 `hit` 只是五类线索之一（`novelty/shift/structure/coverage/hit`），强度只按**规模 + 首见**算，**不读 `rule_severity`**（D4 + `app/analysis/candidates.py:24`）。智能体可以整体不领 `hit`。

推论到界面：
- "有多少条命中"本身不是优先级，不能放在"态势"第一屏当解读对象；
- 事件中心的价值要从"威胁台账"改写成"线索的原始记录 + 人工溯源入口"；
- **不要新增**按级别排序（现有 `SORTS` 只有 `recent`/`oldest`/`count`，`events-panel.tsx:133-137` 本来就没有），也不要用文案暗示"高 = 先看"。这是一条"别加"，不是"要删"。

### 红线三｜结论必须带归属，否则不可用

判断权转移给智能体之后，界面的义务反而变重了：它必须让人看得出**这条结论是谁在什么成本下、基于哪些证据、以什么理由结束的**。契约给的字段是 `verdict / confidence / evidence_refs / terminal_reason / tools_used / duration_ms / anchors / claimed_by`，共 8 项。

推论到界面：
- 缺 `terminal_reason` → "查了没证据"（线索质量差）与"没查完"（预算不够）混为一谈，处置动作相反；
- 缺 `anchors` → 看不出这条结论影响哪些资产，覆盖率的"分析过"就只是个数字；
- 缺 `claimed_by` → 多令牌部署时分不清是谁干的（派工队列已有此列，事件侧没有）。

### 一句话的界面定位

**这不是"NDR 的威胁仪表盘"，而是"采集方的运行台 + 派工方的调度台 + 智能体结论的陈列窗"。** 首屏该回答"我采得全不全、派得出去吗、智能体在干活吗"，而不是"今天有几个高危"。

短期：撤按钮，改为「立即按一次门铃」（需要新端点，或用一个只读的"下次冷却结束时间"替代）；长期等后端确认到底要不要给门铃加重试。

#### P1-5 事件级「忽略」是一本独立账，不影响派工、不写结论

**现状** `events-panel.tsx:985-1000`（忽略/加白）、`:1264-1292`（忽略确认弹窗，文案"忽略不可逆"）。

**为什么不成立**
- 忽略只置 `ignored`（`hits.mark_ignored`），而 `hit` 线索在事件**落库那一刻**就已经入队（`runner.py:311` `candidates.enqueue_hit(...)`），忽略**不会撤回任务**，智能体仍可能来查；
- 忽略不写 `analysis_results`，所以"已忽略"与"误报"是两本账。用户点"忽略"时心里的意思是"这条我看过、不用管了"，而系统里这句话只有智能体能说（`verdict=false_positive`）。

**改成什么**
- 弹窗文案改成："忽略只把这条从默认列表藏起来，**不代表判定，也不会撤回已派工的分析**。要让它不再打扰分析，请走『精准抑制』（需证据）或让智能体在结案时判 `false_positive`。"
- 按钮名「忽略这条」→「**从列表隐藏**」；
- 「已忽略」Stat（`:608-612`）改名「已隐藏」，避免与 verdict 混淆。

#### P1-6 事件列表没有资产上下文

**现状** 列表 7 列（`events-panel.tsx:158-175`）：主机 IP、事件类型（次数）、来源、**级别**、命中次数、事件数、最近。没有主机名/重要级别/责任人。

**为什么不成立**
契约 §3 明写 `asset_context` 是"判严重度的唯一依据"，且"没登记 ≠ 不重要，必须显式区分"。界面把 IP 裸着摆出来，运维无法判断"这条值不值得现在看"，只能自己去资产页搜 —— 而这个判断本该由台账支撑。

**改成什么**
列表 IP 列下加一行小字：`主机名 · 重要级别`（未登记显示"未入库"），概览加一个「未入库资产命中」计数（后端 `asset_context` 已能区分）。这同时能让"重要级别"这个字段真正被用起来（见 #11）。

#### P1-7 行为画像的措辞把统计说成判定

**现状**（`behavior-panel.tsx`）
- `:112` "生效中（已过观测期，参与 2σ 判定）"
- `:207` "判定理由：" / `:215` "本轮没有异常理由"
- `:246-254` 处置按钮"标记误报 / 确认" + "判误报后该实体在 suppress 天内不再参与打分"
- `:513` "…达到阈值才算异常并写进摘要标签推给智能体"
- `:1226-1260` 处置弹窗"给这条画像告警打上结论"

**为什么不成立**
2σ 偏离和画像风险分都是**客观统计**（NDR 的职责范围内），但"判定理由""打上结论"这类词让读者以为这是对攻击的定性。真正的定性在 `complete_task`。另外 `:513` 描述的"推摘要标签"在新架构下已不存在。

**改成什么**
- `判定理由` → 「**偏离项**」（值是"失败率突增"这类事实，不是结论）；
- `标记误报 / 确认` → 「**画像降权 / 标记已知**」，并在弹窗里写清"这只影响该实体以后的打分权重，**不是对事件的结论**（结论由智能体交回，见分析中心）"——对应契约 §6 `record_disposition` 的作用域；
- `:513` 删掉"写进摘要标签推给智能体"，改为"达到阈值的偏离会作为 `baseline_deviation` 来源写入命中事件（同一张表、同一套事件 ID）"。

#### P1-8 画像列表的「风险」与「后验」两个 0~1 并列，没有任何口径说明

**现状** `behavior-panel.tsx:859` 表头「风险」**无 tooltip**；`:860-864` 表头「后验」有 tooltip「似然比后验概率（0~1）；llr 打分时列表按它排序」。两列都是 0~1、都等宽、都右对齐，视觉重量完全一致。

**为什么不成立**
这是两个**不同的数学**，读起来却像同一个数的两种写法：
- **风险** = 多路理由**加权累加**（`behavior-panel.tsx:876` `risk_score`），是"这一轮偏离有多重"的合成分；机制文档 §5.2 专门反思过这套加和法（"三个弱信号 ≈ 一个强信号"），所以它天然需要一句限定；
- **后验** = 似然比后验概率，是"单路证据有多可信"，只在 llr 打分模式下用于排序。

两者都**不是**攻击概率，但界面上只有「后验」被解释了，「风险」反而是更容易被误读成"风险 80% 就是八成是攻击"的那一个。

**改成什么**
- 「风险」表头补 tooltip：「加权累加值（0~1），**不是攻击概率**；过阈值才会写成 `baseline_deviation` 命中事件」；
- 「后验」tooltip 补一句「仅在 llr 打分模式下参与排序，与『风险』不是同一套算法」；
- 区块 help（`:788`）加一句总口径：「风险＝加权累加，后验＝似然比后验；两者都是统计量，判断结论由智能体交回」。
- **不合并两列**：它们服务于不同排查路径（"哪台最重"看风险，"哪条证据最硬"看后验），合并会丢信息。这是**加口径**的问题，不是删列的问题。

#### P1-9 `/config/storage` 的五段速率与「旁路检测器」还在报退役链路

**现状**
- `logstash-panel.tsx:369-390`「五段速率（10 分钟）：扫描 X/秒 · 命中 Y/分 · **摘要 Z/分** · **投递 W/分** · 分析 V/分 · 模型容量 U/分」；
- `logstash-panel.tsx:392-412`「旁路检测器：**本分钟投递** X/上限 · 待检测 · **待分析**」；
- 该面板由 `/config/storage` 挂载（`app/config/storage/page.tsx:20`），**不是** `/config/collect`（那页是 `ZeekPanel`，`app/config/collect/page.tsx:13`）。

**为什么不成立**
`digests_per_min` / `delivered_per_min` 读的是 `d_digest` / `d_delivered`（`detector.py:243-244`），`queue_digest` 读的是攒批队列；三者在默认派工模式下全部恒 0（P0-1 的同一条证据链）。后果与总览不同：五段速率的读法是"取最小的一段当瓶颈"（`status-charts.ts:452` 注释同源），所以它会**稳定地把瓶颈指向"投递"**，而投递这一环在新架构里已经被门铃取代 —— 人去调"投递"是白跑。旁路检测器那行的「待分析」同理，会让人以为有一堆摘要堆积待投。

**改成什么**
- 五段速率 → 三段（入队 / 扫描 / 命中）；若需第四段，接「派工队列」；
- 「本分钟投递 X/上限」→「门铃：已叫醒 N / 失败 M」（数据取 `push.status.sent/retry_failed`，见 P1-4），删掉 `rate_limit_per_minute` 这个已无意义的"上限"；
- 「待分析」→「待派工」（`/api/analysis/stats` 的 `pending`）；
- 存储配置区块（ES 索引、保留期、裁剪）**一个字都不动** —— 那些是真实在用的。

### 4.5 首屏"英雄数字"的归属规则（team-lead 裁决 2 的落地口径）

**规则：首屏只允许一个 28px，且必须是一个"与判断无关的客观量"。**

| 页面 | 28px 的那一格 | 其余格的重量 | 判据 |
|---|---|---|---|
| 命中事件 | **命中总数**（窗口内，不含已隐藏） | 全部 `md` | "量级"是运维第一眼要知道的；「级别（高危以上）」降 `md` 且去色，避免排版替平台下判断 |
| 派工队列 | **待派条数** | 其余 `md` | 它是"有没有活/堵没堵"的唯一直接信号 |
| 运营中心 | **事件入库覆盖率**（或队列积压） | 其余 `md` | 采集完整性是这一页的存在理由 |
| 精准抑制 | 保持现状（四格等重 `md`） | — | 该页的"重量"应给 mode 对照带，不该再造主角数字 |

**接受混排带来的栅格观感**（3 格不等重、可能有高度差）：这是刻意的不对称 —— 如果三格等重，读者会把三个数当同一层级比较，而它们本来不是一个量级的东西。实现上 28px 那一格用 `items-start` 对齐、其余格 `items-center`，避免"三个数字蹲在同一条基线上"的错觉。
